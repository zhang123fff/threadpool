一、概述
--------
Po Threadpool 是一个基于 C++20 的固定大小线程池，使用 std::counting_semaphore 
进行任务通知，并通过外部多态容器（con::container）存放任务。支持任务提交、
异常隔离、容量控制、安全停止及重启。经过多项测试验证，功能正确、运行稳定，
性能处于有锁线程池的中等水平。

二、公共接口详细说明
-------------------------------------------------------------------------------
1. 构造函数
   threadpool() noexcept
       - 行为：创建未启动的空线程池，running = false，信号量计数器为 0，
              任务计数和线程计数为 0。不分配任务容器。
       - 异常：不抛出。

   threadpool(pool_command com)
       - 参数：com - 目前支持 pool_command::instant（预留扩展，实际无操作）。
       - 行为：调用默认构造函数，然后处理命令（当前为空）。
       - 异常：不抛出。

2. 析构函数
   ~threadpool()
       - 行为：如果线程池正在运行（is_running() == true），则调用 
               exit_preperation() 尝试安全停止所有线程。若已停止则无操作。
              注意：exit_preperation() 会阻塞直到所有线程退出。
       - 异常：不向外抛出（内部捕获所有异常，但仍建议用户主动调用 end()）。
       - 注意：由于析构可能阻塞（最多取决于退出轮询），应避免在析构中长时间等待。

3. start(size_t th_num)
       - 参数：th_num - 要启动的工作线程数量，必须满足 0 < th_num <= 5000。
       - 返回值：无。
       - 行为：如果线程池已运行，抛出 std::logic_error；否则创建一个 
               con::blocking_queue 作为任务容器，设置 running = true，
               创建 th_num 个工作线程并开始执行。
       - 异常：
           - std::invalid_argument ：th_num == 0 或 th_num > thread_maximum。
           - std::logic_error ：线程池已经在运行（重复 start）。
           - 若线程创建过程中抛出异常，已创建的线程会被保留（部分成功），
             异常会传播给调用者。此时线程池可能处于半启动状态，需要调用者
             负责调用 end() 清理。

4. end()
       - 返回值：无。
       - 行为：若线程池未运行，抛出 std::logic_error。否则设置 running = false，
              进入退出准备阶段。该阶段会循环检查 thread_num，当其为 0 时退出。
              在循环中若线程计数未减少，则会向队列推入一个空任务（以唤醒阻塞在
              信号量上的线程），并每次休眠 10ms。一旦所有线程退出，join 所有
              线程并清空线程向量（保留容器空间）。
       - 异常：
           - std::logic_error ：线程池已停止（重复 end）。
           - 注意：在正常条件下 end() 能安全返回，但在极端并发场景下，
             理论上存在极低概率的死锁风险（见已知问题）。
       - 退出延迟：≤ 10ms（取决于轮询间隔）。

5. is_running() const noexcept
       - 返回值：bool，指示线程池是否正在运行。
       - 行为：以 acquire 内存序原子读取 running 标志。

6. enqueue
   template<typename...Args, typename Ret>
   auto enqueue(const std::function<Ret(Args...)>& func, Args...args)
     -> std::future<Ret>
       - 参数：func - 一个 std::function 包装的可调用对象。
               args... - 调用参数（按值传递）。
       - 返回值：std::future<Ret>，用于获取任务执行结果。
       - 行为：
           - 检查线程池是否运行，否则抛出 std::runtime_error。
           - 将 func 和 args 包装为 std::packaged_task，获取关联的 future。
           - 调用 push() 将任务入队。若 push 返回 false（队列满），抛出异常。
       - 异常：
           - std::runtime_error("enqueue 失败: 线程池已经终止") ：线程池未运行。
           - std::runtime_error("enqueue : push失败") ：任务队列满被拒绝。
           - 其他：任务内抛出的异常会通过 future::get() 重新抛出，且工作线程
             会捕获并打印错误，不影响其他任务。
       - 注意：当前实现要求显式构造 std::function，不支持直接传入 lambda 等。
              参数按值传递，可能有额外拷贝开销。

三、行为特性与属性
-------------------------------------------------------------------------------
- 线程数：固定，由 start() 指定，运行期间不可变。
- 最大并发任务数：task_maximum = 5,000,000（入队上限）。
- 同步机制：两层同步
   1) std::counting_semaphore 实现任务就绪通知，避免锁竞争。
   2) 任务容器（con::blocking_queue）内部可能使用 mutex 保护共享队列，
      与信号量形成双重同步。
- 任务拒绝：当原子计数器 task_num 达到 task_maximum 时，push 返回 false，
  enqueue 抛出异常，而非阻塞等待。
- 异常安全：
   - 工作线程捕获所有任务异常，打印错误并继续运行，保证线程不退出。
   - push/pop 在容器操作失败时回滚信号量或计数器，防止资源泄漏。
- 重启支持：end() 后可再次调用 start()，任务容器和线程向量的内存空间被保留。
- 退出策略：通过轮询 + 推送空任务唤醒阻塞线程，轮询间隔 10ms。
  退出时更新 th_num 的本地副本（th_num = get_thread_num()），动态跟踪线程退出，
  避免过早停止推送空任务，确保所有阻塞线程最终被唤醒。

四、性能指标（Release x64, 8核16线程 CPU）
-------------------------------------------------------------------------------
  空任务吞吐量              : ~0.65 M tasks/sec (纯框架调度开销 ~1500ns/任务)
  计算任务吞吐量            : ~640 K tasks/sec (质数判定约 15μs/任务，框架占比小)
  调度延迟（最小）          : ~800 ns
  调度延迟（平均）          : ~4900 ns
  调度延迟（最大）          : ~28 μs
  退出延迟                  : ≤ 10 ms（轮询间隔）

  注：数值受硬件和系统负载影响，但可反映相对水平。

五、适用与不适用场景
-------------------------------------------------------------------------------
  适用：
    - CPU 密集型任务，单任务执行时间 > 20μs，此时框架开销可忽略。
    - 需要固定并发数、防止资源过载的应用。
    - 需要异常隔离，个别任务失败不影响整体。
    - 需要停止并重启线程池的场景。

  不适用：
    - 极端低延迟任务（要求调度延迟 < 500ns）。
    - 海量极短任务（<1μs），框架开销成为瓶颈。
    - 需要动态增减线程的弹性系统。
    - 需要复杂调度策略（如优先级、工作窃取）。

六、已知问题与潜在风险
-------------------------------------------------------------------------------
1. 退出机制仍有理论风险：
   虽然 exit_preperation() 中加入了 th_num = get_thread_num() 更新，能在线程退出
   后正确继续推送空任务唤醒剩余线程，但若出现 push 失败（如 task_num 异常），
   可能导致无法唤醒线程而永久阻塞。正常操作下该情况几乎不会发生。

2. 双重同步导致性能瓶颈：
   任务容器内部的 mutex 与信号量共同作用，每次任务入队/出队需要两次同步操作，
   大幅增加了调度延迟和空任务开销。

3. 多态虚函数开销：
   容器通过 con::container 基类指针操作，push/pop/empty 均为虚函数调用，
   增加额外的间接跳转成本。

4. enqueue 接口局限：
   仅接受 std::function<Ret(Args...)>，使用不便且导致额外动态内存分配。
   参数按值传递可能引起不必要的拷贝，无法完美转发。

5. 线程创建部分失败处理不够完善：
   若 start() 中部分线程创建失败，已启动的线程仍在运行，但调用者获得的异常中
   未提供清理方法，可能导致资源泄漏（除非调用 end()）。

6. 信号量计数上限绑定 task_maximum：
   sem.release() 超过最大值会抛出 std::system_error，当前代码通过 CAS 控制
   task_num 保证不超限，但任何疏忽（如退出时推送过多空任务）可能触发此问题。

7. 工作线程函数参数未使用：
   thread_executing_program1(std::atomic<size_t>& th_num) 接收 th_num 参数但
   未使用，线程增减直接操作成员变量 thread_num，参数冗余。

等核心功能。经过 14 项严格测试，包括基本功能、并发正确性、原子递增、异常隔离、

在性能方面，受限于内部容器的锁机制和双重同步，空任务调度开销约 1.5μs，在真实
计算任务中（如 15μs 的质数判定）框架开销占比 <10%，因此对于中等粒度以上的并行
任务表现良好。线程池具有固定线程数、强异常隔离、重启能力等优点，适合多数常规
并发处理需求。

以及 enqueue 接口的通用性有待提升。这些可在后续版本中迭代改进。

总体而言，该线程池是一个可靠、稳定的并发基础组件，可作为学习参考或轻量生产环境
的基石。
